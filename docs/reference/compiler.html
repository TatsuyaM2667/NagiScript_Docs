Lexer (字句解析)

処理

  1. ソースコードをトークンに分割
  2. キーワード、識別子、リテラルを認識
  3. 行番号・列番号を追跡

トークンタイプ

rust
enum Token {
    // キーワード
    Fn, Val, Var, Struct, Enum, If, Else, For, While, Match,
    Return, Break, Continue, Import, Export, Async, Await,
    
    // リテラル
    IntLit(f64), FloatLit(f64), StrLit(String), BoolLit(bool),
    
    // 識別子
    Ident(String),
    
    // 演算子
    Plus, Minus, Star, Slash, Percent,
    Eq, Neq, Lt, Gt, Leq, Geq,
    And, Or, Not,
    AmpAmp, StarStar, Question,
    
    // 区切り
    LParen, RParen, LBrace, RBrace, LBracket, RBracket,
    Comma, Colon, Semicolon, Dot, Arrow,
    
    // 特殊
    Eof, Newline, Indent, Dedent,
}
現行仕様（v0.2.0）

実際にキーワードとしてトークン化されるのは fn val var if else for while match struct enum impl unsafe extern export return in as break continue true false です。import / async / await はトークン区分として残っていますが未実装です。and / or / not キーワードは存在しないため、論理演算は && / || / ! を使用してください。

Parser (構文解析)

処理

  1. トークン列から抽象構文木 (AST) を構築
  2. 構文ルールに従ってノードを作成
  3. エラーメッセージを生成

Semantic Analysis (意味解析)

処理

  1. 型チェック
  2. 名前解決
  3. 借用チェック
  4. エラー検出
現行仕様（v0.2.0）

名前解決は同一ファイル内の識別子解決のみです。import によるモジュール解決は未実装のため、現行では複数のファイルに分割できず、1 つの main.ngs で完結させます。

型チェック

rust
fn check_expr(expr: &Expr, env: &mut Env) -> Result<Type, Error> {
    match expr {
        Expr::IntLit(_) => Ok(Type::I32),
        Expr::Ident(name) => env.lookup(name),
        Expr::BinaryOp { op, left, right } => {
            let left_ty = check_expr(left, env)?;
            let right_ty = check_expr(right, env)?;
            
            if left_ty != right_ty {
                return Err(Error::TypeMismatch(left_ty, right_ty));
            }
            
            Ok(left_ty)
        }
        // ...
    }
}

IR Lowering (中間表現変換)

処理

  1. AST → HIR (High-level IR) 変換
  2. HIR → MIR (Mid-level IR) 変換
  3. 型消去 (Type Erasure)
  4. 単型化 (Monomorphization)

単型化の例

ngs
// 元のコード
fn add<T: Numeric>(a: T, b: T) T {
    a + b
}

val x = add(10, 20)      // T = i32
val y = add(1.5, 2.5)    // T = f64
rust
// 展開後
fn add_i32(a: i32, b: i32) i32 {
    a + b
}

fn add_f64(a: f64, b: f64) f64 {
    a + b
}
現行仕様（v0.2.0）

上記は単型化の動作説明用です。ユーザーコードでは fn add<T: Numeric>(a: T, b: T) T のような型パラメータ付き関数は現行では限定的で、Vec2<T> 等のジェネリクス構造体は未実装です。実コードでは戻り値を -> 構文で書き、ブロック末尾の暗黙 return ではなく return を明示してください。

LLVM Backend

処理

  1. MIR → LLVM IR 変換
  2. 最適化パスの適用
  3. ネイティブコード生成

LLVM IR 生成

rust
fn codegen_expr(expr: &Expr, builder: &Builder) -> IntValue {
    match expr {
        Expr::IntLit(n) => builder.const_int(*n),
        Expr::BinaryOp { op, left, right } => {
            let l = codegen_expr(left, builder);
            let r = codegen_expr(right, builder);
            
            match op {
                BinOp::Add => builder.build_add(l, r),
                BinOp::Sub => builder.build_sub(l, r),
                BinOp::Mul => builder.build_mul(l, r),
                BinOp::Div => builder.build_signed_div(l, r),
                // ...
            }
        }
        // ...
    }
}
現行仕様（v0.2.0）

整数 / 浮動小数点型は LLVM の対応する型にほぼ 1:1 でマップされます（i32 → LLVM i32、f64 → LLVM double 等）。既知の問題として、List<T> のコード生成で zext i64 to i64 エラーが発生しリンクに失敗するため、現行では構造体 + 値渡しの利用を推奨します。

Wasm Backend

処理

  1. MIR → WAT (WebAssembly Text) 変換
  2. WAT → Wasm バイナリ変換
  3. 型定義ファイル (.d.ts) 生成

WAT 生成

wat
(module
  (func $add (param i32 i32) (result i32)
    local.get 0
    local.get 1
    i32.add
  )
  (export "add" (func $add))
)
現行仕様（v0.2.0）

Wasm 出力は nagiscript wasm main.ngs [-o PATH] で行います（.wat、可能なら .wasm + 型定義ファイル .d.ts）。Wasm / C へのエクスポートは export "C" fn 形式が正しい書き方です（export fn とは書けません）。

ngs
export "C" fn add(a: i32, b: i32) -> i32 {
    return a + b
}

最適化

LLVM 最適化パス

  1. Constant Folding: 定数畳み込み
  2. Dead Code Elimination: 死コード除去
  3. Inlining: 関数インライン化
  4. Loop Unrolling: ループ展開
  5. Vectorization: ベクトル化

コンパイル時の最適化レベル

現行仕様（v0.2.0）

現行 CLI の出力コマンドは次のとおりです。--opt 等の最適化レベル指定は現行では提供されません。

bash
nagiscript wasm main.ngs          # .wat を出力
nagiscript wasm main.ngs -o out   # out.wat / out.wasm + out.d.ts を出力

パフォーマンス

コンパイル速度

  • 字句解析: O(n)
  • 構文解析: O(n)
  • 意味解析: O(n log n)
  • IR 変換: O(n)
  • コード生成: O(n)

実行時パフォーマンス

  • 関数呼び出し: C ABI と同等
  • メモリアクセス: ヒープ確保のみオーバーヘッド
  • エラーハンドリング: Result 型による分岐
